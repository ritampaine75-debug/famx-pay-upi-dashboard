================================================================================
1. PRODUCT SUMMARY
================================================================================

Product name: FamX Pay
Positioning: A seller-oriented UPI payment-link and transaction-monitoring dashboard for India.
Primary users:
- Seller/merchant who creates payment requests.
- Customer who opens a payment link and pays through a UPI app.
- Authorized platform administrator who manages access and service health.

Core user journey:
1. Seller signs in.
2. Seller completes the secure setup wizard.
3. Seller tests Gmail IMAP authentication.
4. The system searches recent mail for FamPay/FamApp-related messages and identifies likely incoming-payment notification patterns.
5. Seller creates a payment order for a specific INR amount.
6. The application creates a unique shareable URL and a QR code containing the correct UPI payment intent.
7. Customer opens the URL, sees amount and merchant details, and can scan the QR or open a supported UPI application.
8. Backend checks eligible email notifications and matches transaction evidence to orders under explicit verification rules.
9. The public checkout and seller dashboard receive status changes in real time.
10. Ambiguous or weakly supported matches go to reconciliation; they must not be automatically treated as confirmed settlement.

Product truthfulness requirement:
- A UPI app launch is not proof of payment.
- A customer screenshot or browser callback is not proof of payment.
- A Gmail message is not inherently authoritative settlement evidence.
- Without an official provider API, reliable bank/merchant settlement feed, or an unambiguous matching reference, the system may only report an email match or a pending reconciliation state.
- Do not market or label this as an official FamPay merchant gateway unless an authorized official integration is actually implemented.

================================================================================
2. PRODUCT GOALS AND NON-GOALS
================================================================================

Goals:
- Create shareable payment requests in INR.
- Create downloadable QR codes and UPI payment intents.
- Provide an attractive customer checkout page.
- Provide a secure Gmail connection test.
- Detect relevant FamPay/FamApp messages and classify likely incoming versus outgoing payment notifications.
- Prevent duplicate transaction records and arbitrary order assignment.
- Show seller-owned orders and transaction activity in real time.
- Use Firebase RTDB and Firestore for distinct, documented purposes.
- Avoid requiring a manually edited .env file.
- Provide a usable setup and diagnostics screen with accurate failure messages.
- Work well on Android mobile browsers and desktop.

Non-goals unless an official integration becomes available:
- Directly debit a customer's bank account.
- Guarantee payment settlement using email alone.
- Impersonate Google Pay, PhonePe, FamPay, or another payment brand.
- Claim official payment-provider affiliation.
- Bypass UPI application or bank security.
- Read unrelated private email content beyond the minimum needed for verification.
- Store card data, UPI PINs, banking passwords, or customer authentication secrets.
- Make production database rules public to simplify development.

Authenticated request fields:

- appPassword for this test request

- overallStatus
- inputValidation
- authentication
- imapConnection
- relevantEmailCount
- incomingCandidateCount

- Rate limits and bounded retries required.

Credential lifecycle:
- Temporary tests may use an in-memory credential for the request, provided it is not logged or persisted.
- For continuous monitoring, provision the credential in a supported encrypted server-side secret store.
- Use least-privilege IAM access.
- Support credential replacement, disablement, and deletion.
- Record only non-secret connection state in Firebase.
- Do not put ciphertext and its decryption key together in the same database.

Monitoring:
- Use a deployed scheduled worker, supported background worker, or suitable server-side process.
- Do not assume a serverless HTTP function remains alive after returning a response.
- Use a configurable, bounded scan interval.
- Respect Gmail provider limits and avoid excessive repeated mailbox searches.
- Use message IDs and transaction IDs for deduplication.
- Minimize email content retention and avoid storing complete message bodies.
- Handle IMAP disconnections, expired credentials, Gmail restrictions, and service outages.
- Display last successful scan and last error accurately.

Email classification:
- Inspect sender address, headers, subject, and relevant message content.
- Treat all email content as untrusted.
- Distinguish incoming receipts from outgoing payments.
- Support HTML and plain-text MIME.
- Sanitize content before any rendering.
- Extract amount, transaction ID, timestamp, counterparty, and reference only when present.
- Record parser confidence and missing fields.
- Never create missing transaction values by guessing.

================================================================================
11. FUNCTIONAL GMAIL TEST CONNECTION AND FAMPAY EMAIL DETECTION
================================================================================

Implement this feature as a real workflow, not a decorative button.

Test Connection steps:
1. Validate Gmail address and App Password input.
2. Open a secure TLS IMAP connection.
3. Authenticate against Gmail.
4. Search a bounded time window, defaulting to 90 days.
5. Find FamPay/FamApp-related candidate messages.
6. Identify likely incoming payment notifications.
7. Identify likely outgoing payment notifications separately.
8. Parse a bounded sample of messages.
9. Return structured test results.
10. Close the IMAP connection.

UI must show separate statuses:
- Input validation.
- Gmail authentication.
- IMAP connectivity.
- Relevant email discovery.
- Incoming notification detection.
- Outgoing notification detection.
- Parsing completeness.
- Credential provisioning.
- Background monitoring.

Expected cases:
- Correct password and matching emails: authentication succeeds and candidates are reported.
- Correct password and no matching emails: authentication succeeds, email discovery warns that none were found.
- Incorrect password: authentication fails with a useful, non-secret error.
- Network failure: show connection failure and retry guidance.
- FamPay mention without a payment receipt: do not count it as an incoming transaction.
- Outgoing receipt: classify separately and exclude from received funds.
- Missing transaction ID or amount: mark incomplete and route to reconciliation where appropriate.

Do not trust display name alone. Do not approve payment from an email merely because its amount matches an order.

================================================================================
12. PAYMENT STATE MACHINE
================================================================================

Use a documented state machine. Suggested order statuses:
- `created`
- `pending`
- `evidence_detected`
- `awaiting_reconciliation`
- `verified`
- `expired`
- `cancelled`
- `verification_failed`

Allowed transitions must be enforced by the backend, not only by the UI.

Examples:
- `created` -> `pending`
- `pending` -> `evidence_detected`
- `evidence_detected` -> `verified` only when configured evidence requirements are met
- `evidence_detected` -> `awaiting_reconciliation` when the match is ambiguous
- `pending` -> `expired` when the server expiration policy applies
- `expired` -> reconciliation state if late evidence appears
- `cancelled` must not be silently turned into verified by a public request

Do not allow the browser to submit an arbitrary next status. Validate each transition server-side and log consequential changes.

Define a separate transaction verification status so an email candidate is not automatically equated with a settled payment.

================================================================================
13. PAYMENT MATCHING AND FRAUD RESISTANCE
================================================================================

Matching priority:
1. Official provider transaction confirmation, if available.
2. Reliable transaction record with an unambiguous unique order/payment reference.
3. Email notification evidence with enough independent fields to make a high-confidence match.
4. Ambiguous email evidence -> reconciliation.

Rules:
- Exact amount match is necessary but not sufficient.
- Check transaction direction.
- Check recipient/seller where reliable evidence exists.
- Check order reference where present.
- Reject duplicate transaction IDs.
- Prevent a single transaction from satisfying multiple orders.
- Do not arbitrarily assign same-amount transactions to the oldest or newest order.
- Use server timestamps and idempotent operations.
- Protect against concurrent processing.
- Maintain an audit trail for manual resolution.
- Never accept client-provided “payment successful” as proof.
- Never rely on screenshots or redirect parameters as settlement proof.

================================================================================
14. UPI URI AND QR GENERATION
================================================================================

Generate a valid UPI payment URI only from validated seller configuration and server-approved order data.

Include supported fields:
- `pa`: verified seller UPI VPA.
- `pn`: payee display name.
- `am`: exact amount in INR.
- `cu`: INR.
- `tn`: safe payment description/reference.
- `tr`: unique order reference when supported.

URL-encode all parameter values. Confirm the intended recipient and amount before displaying the payment link.

QR requirements:
- Generate a real QR code that can be scanned by compatible UPI applications.
- Download as PNG.
- Offer a print-friendly layout.
- Show merchant name and amount outside the encoded QR for readability.
- Do not include credentials or private email information.
- Test generated URIs with unit tests and QR decoding where possible.
- Make clear that app support varies by device and UPI app.

Payment initiation is not payment confirmation. Do not interpret a successful deep-link launch as a successful transaction.
